# Releasing

There are two kinds of release:

- **Code.** A GitHub release, tagged `vX.Y.Z`. Each one builds the container image
  `ghcr.io/monarch-initiative/monarch-phenologs:vX.Y.Z`, which holds the code and its locked environment.
- **Data.** One release per Monarch KG version and prediction network, made by running the image on that KG and
  published to `gs://data-public-monarchinitiative/phenologs/alpha/<kg version>/<network>/`
  (`https://data.monarchinitiative.org/phenologs/alpha/`).
  - The dashboard (GitHub Pages) lists the data releases from `releases.json` there. A new data release needs no
    site deploy.
  - Each data release records the KG, PHENIO and code versions that made it.

## Making a data release

Run the image's steps in order on a fresh project directory. Scripts are at `/app/python` and run from any working
directory. No versions need to be given:

- Step 01 takes the newest Monarch KG release (`monarch-kg/latest/metadata.yaml`) and the PHENIO it was built with.
- It writes both to `monarch_kg/versions.json`, where the later steps read them.
- `-gv 2026-03-06` asks for another KG. A date Monarch never released is looked for in `monarch-kg-dev/`.

| step | command | needs (old cluster settings, a starting point) |
|---|---|---|
| 01 | `01_download_and_setup.py -p $PROJECT` | internet, 8 GB, ~6 GB disk |
| 02 | `02_kg_data_extraction.py -p $PROJECT` | 8 GB |
| 03 | `03_compute_phenologs_randomized_trials.py -p $PROJECT -n 1000 -c $CPUS -taxon_id 9606 -prd disease -seed 1` | 128 cpus, 256 GB, 6 h |
| 04 | `04_compute_phenologs.py -p $PROJECT -c $CPUS -taxon_id 9606 -prd disease` | 8 cpus, 32 GB |
| 05 | `05_compute_phenologs_fdr_data.py -p $PROJECT -taxon_id 9606 -prd disease` | 8 GB |
| 06 | `06_phenologs_compute_ortholog_to_phenotype_rankings.py -p $PROJECT -taxon_id 9606 -prd disease -fdr 0.05 -kneighbs 1000 -rank_metric hg -rank_type gene` | 8 GB |
| 06, candidates | `phenologs_disease_gene_candidate_rankings.py -p $PROJECT -taxon_id 9606 -prd disease -fdr 0.05 -kneighbs 1000 -rank_metric hg` | 8 GB |
| 07 | `07_build_release.py -p $PROJECT -c $CPUS -m <memory, e.g. 8GB>` | 4 cpus, 8 GB, under a minute |

- **Order.** 03 and 04 both need only 02's output, so they can run side by side. 05 needs both.
- **Output.** `$PROJECT/release/<kg version>/disease/`, about 30 MB. This folder is the release; everything else
  in `$PROJECT` is working data that can be deleted once the release is published.
- **Repeats.** The trials are seeded, so the same KG, code and seed give the same release.
- **Measured resource peaks.** The paper runs' Nextflow traces on the cluster (`PHENOLOGS_RESEARCH/<pipeline>/runs/`)
  have the measured peaks.
- **Checking a release before publishing.** Copy the release folder to a machine with a browser, then:

      python dashboard/serve.py -p $PROJECT      # http://localhost:8765

## Publishing a data release

Needs write access to `gs://data-public-monarchinitiative/phenologs/`. Order matters:

```
python /app/python/08_update_release_list.py -p $PROJECT            # the very first release: add -r none
gcloud storage rsync -r $PROJECT/release/2026-03-06/disease gs://data-public-monarchinitiative/phenologs/alpha/2026-03-06/disease
gcloud storage rsync -r --delete-unmatched-destination-objects \
    gs://data-public-monarchinitiative/phenologs/alpha/2026-03-06/disease gs://data-public-monarchinitiative/phenologs/alpha/latest/disease
gcloud storage cp $PROJECT/release/releases.json gs://data-public-monarchinitiative/phenologs/alpha/releases.json
```

1. **08** fetches the published `releases.json`, puts the project's releases in it (in place of earlier builds of the
   same folder), and writes `$PROJECT/release/releases.json`. Run it right before uploading, so the list it adds to
   is current. It stops if the published list can't be read, so a failed fetch never drops the published releases.
2. **The release folder** goes up before the list, so the site never lists a release that isn't there yet.
3. **`latest/<network>/`** is a copy of the newest release of that network, a stable address for downloads. 08 says
   which release is the newest; refresh `latest/` only when it is the one just built (an older KG rebuilt later is not).
4. **`releases.json`** goes up last.

Things to know:

- **Skip.** If the published `releases.json` already lists `<kg version>/<network>/`, that release exists, so
  nothing needs to run.
- **The alpha folder** also holds older files of other kinds. Never sync it as a whole with deletion.
- **Folder index pages** on data.monarchinitiative.org are regenerated by Monarch's indexer. The site doesn't need them.

## Making a code release

- **Version.** Set it in `pyproject.toml`, merge to main, and publish a GitHub release tagged `v<that version>`.
  The image workflow (`.github/workflows/image.yml`) builds and pushes
  `ghcr.io/monarch-initiative/monarch-phenologs:v<version>`, and moves `latest` to it.
- **Pulling.** On the cluster: `apptainer pull docker://ghcr.io/monarch-initiative/monarch-phenologs:v<version>`.
  The first image pushed makes the package; set it to public once, in its settings on GitHub.
- **Iterating.** The same workflow can be run by hand (Actions, then Run workflow) from any branch, under any tag.
  - Pushing a tag again moves it to the new image.
  - Old images can be deleted in the package settings.
  - Each release records the code that built it as `code_version`: the tag, the commits since it and the commit,
    e.g. `v0.4.0-0-g1a2b3c4`. A moved tag never hides which code made a release.
- **Pinning.** Data releases are made with a pinned image tag. Moving to a new code release is a one-line change in
  the release pipeline's settings.
